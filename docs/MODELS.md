## スコアリングモデル

**10要素**の評価項目を加重平均して総合スコアを算出するモデルです。

> **変更履歴**: 専門家会議（2026/01/03）の議論を経て、7要素→10要素に拡張。
> 騎手15%→8%、上がり3F 7%→10%、馬場適性・枠順・調教師を新規追加。

### 実装ファイル

```
src/domain/entities/Horse.ts       # スコア計算ロジック（リッチドメインモデル）
src/domain/entities/Jockey.ts      # 騎手スコア計算
src/domain/entities/Trainer.ts     # 調教師スコア計算
src/domain/services/ScoringOrchestrator.ts  # オーケストレーター
src/commands/CalculateScore.ts     # スコアリングコマンド
src/constants/ScoringConstants.ts  # 定数定義
```

### スコア構成（10要素）

| カテゴリ | 評価項目 | 重み | 説明 |
|---------|---------|------|------|
| 馬の能力・実績 | 直近成績 | 22% | 直近5戦の着順・人気・オッズを評価 |
| | コース適性 | 15% | 会場（中山等）での過去成績 |
| | 距離適性 | 12% | 目標距離±300mでの成績 |
| | 上がり3F能力 | 10% | レース終盤での差し・追い込み能力（標準化済み） |
| 実績 | G1実績 | 5% | G1レースでの入賞実績 |
| コンディション | ローテ適性 | 10% | 出走間隔と成績の関係 |
| | 馬場適性 | 5% | 馬場状態（良/稍重/重/不良）別の成績 |
| 人的要因 | 騎手能力 | 8% | 会場成績・G1成績・調教師コンビ成績 |
| | 調教師 | 8% | G1/重賞での厩舎実績（信頼度補正あり） |
| 枠順 | 枠順効果 | 5% | 中山2500m内枠有利の補正 |

**合計: 100%**

### 計算式

```
総合スコア =
    (直近成績 × 0.22) +
    (コース適性 × 0.15) +
    (距離適性 × 0.12) +
    (上がり3F × 0.10) +
    (G1実績 × 0.05) +
    (ローテ × 0.10) +
    (馬場適性 × 0.05) +
    (騎手能力 × 0.08) +
    (調教師 × 0.08) +
    (枠順効果 × 0.05)
```

| 直近2戦目 | 25% |
| 直近3戦目 | 20% |
| 直近4戦目 | 12% |

| 着順 | 基本点 |

### 2. コース適性スコア（15%）

指定会場での過去成績を評価します。

#### 計算方法

```
基本スコア = 会場での勝率 × 100
```

#### 信頼度係数

| 会場での出走数 | 係数 |
|--------------|------|
| 3走以上 | 1.0 |
| 2走 | 0.8 |
| 1走 | 0.6 |
| 0走 | 0.5（デフォルト50点） |

### 3. 騎手能力スコア（8%）

騎手の過去成績を4つの観点から評価します。

#### 構成要素

| 要素 | 重み | 説明 |
|------|------|------|
| 会場勝率 | 30% | 指定会場での勝率 |
| 会場G1勝率 | 30% | 指定会場のG1レースでの勝率 |
| 全体勝率 | 20% | 全コースでの勝率 |
| 調教師コンビ勝率 | 20% | 該当馬の調教師とのコンビでの勝率 |

#### 計算式

```
騎手スコア = (会場勝率スコア × 0.30) + (会場G1勝率スコア × 0.30) +
             (全体勝率スコア × 0.20) + (調教師コンビ勝率スコア × 0.20)
```

#### 信頼度補正

| 会場出走数 | 係数 |
|-----------|------|
| 50走以上 | 1.0 |
| 20〜49走 | 0.9 |
| 10〜19走 | 0.8 |
| 10走未満 | 0.6 |

#### 最適間隔

3〜12週間の間隔での好走率を評価します。

```

|------------------|------|
| 3走以上 | 1.0 |
| 2走 | 0.8 |
| 1走 | 0.6 |
| 0走 | 0.5（デフォルト50点） |

## 機械学習モデル

L2正則化ロジスティック回帰に、レース内 softmax（conditional logit）を組み合わせた
確率予測モデルです。

### 実装ファイル

```
src/features/FeatureBuilder.ts     特徴量の構築（as-of）
src/models/MachineLearningModel.ts 学習・予測・walk-forward検証
```

### 設計の前提

1. **確率を捏造しない**
   旧実装にあった `rfProb = 0.5 + 平均スコア × 0.35` のような手作り式は全廃した。
   出力される確率はすべて学習済みモデル（または市場の暗黙確率）由来である。
2. **レース内で正規化する**
   1着になるのはレースで1頭だけなので、単勝は softmax で **合計1**。
   3着以内は3頭なので、複勝は **合計3** に較正する。
3. **as-of（リーク遮断）**
   特徴量は各レースの `race_date` **より前** のデータだけで組む。
   集計テーブル（`horse_course_stats` 等）は「現時点の全結果」なので使わず、
   `race_results` からの as-of 集計に置き換えている。
4. **予測時点は「発売締切直前」**
   特徴量に人気順位・単勝オッズという市場情報を含めているため、
   このモデルが成立するのは **締切時点の人気／オッズが確定した後** である。
   人気順位は締切時点で確定する **事前情報** なので、
   「レース結果に依存する情報の混入」という意味の look-ahead では **ない**。
   ただし裏返すと、**締切より前（前日・当日朝）に予測したい用途には使えない**。
   学習データ（結果ページ由来）には常に人気があるのに対し、
   これから走るレースを出馬表から予測する場合は人気が取れないことがあり、
   そのときは `hasPopularity = 0`（欠損）として学習時に見ていない領域に入る。
5. **「妙味」は市場との差ではなく、市場の誤差の予測**
   市場情報をモデルの主軸特徴量に入れた以上、
   `predict` が出す「妙味 = 単勝確率 − 市場暗黙確率」は
   市場と独立な指標ではない。モデルは市場を入力として受け取ったうえで
   「市場がどちらへどれだけずれているか」を推定しているので、
   妙味は **モデルが推定した市場の誤差** と読むべきである
   （市場を上回る独立した情報源を持っている、という意味ではない）。

### 2つのモデル

| モデル | 目的変数 | 出力 |
|--------|---------|------|
| 単勝モデル | 1着かどうか | 線形スコアをレース内 softmax → 単勝確率（合計100%） |
| 複勝モデル | 3着以内かどうか | シグモイド → レース内で合計300%へ較正 |

#### 学習パラメータ

| パラメータ | 内容 |
|-----------|------|
| 正則化 | L2（係数のみ。バイアスには掛けない） |
| L2強度 λ | `ml --validate` では **ブロックごとに内側分割で自動選択**。単発学習の既定は 100 |
| 特徴量標準化 | **学習データのみ** から平均・標準偏差を計算し、推論時に再利用 |
| 最適化 | フルバッチ勾配降下。損失が増えた反復では学習率を半減 |
| 収束判定 | 損失の改善が `tolerance` 未満で打ち切り（既定 1e-7 / 最大500反復） |
| 学習の最小データ量 | 50出走行（未満なら学習せず、市場の暗黙確率を返す） |

#### λ の既定値が 100 である理由

旧既定は 1.0 だったが、実データ（227レース / 3,293出走行）の内側分割では
学習窓204レースのブロックで候補 `[0.01, 0.1, 1, 10, 100]` のうち **100 が選ばれた**。
34次元を数百レースで学習するとき、弱い正則化は素直に自信過剰へ倒れる
（λ=1 のときの較正テーブルでは予測50〜60%の帯の実績勝率が18.5%しかなかった）。

`ml --validate` はこの既定値を使わず毎ブロックで選び直すので、
この定数が効くのは `ml --train` / `predict` の単発学習だけである。

### 特徴量

ルールベース10要素「だけ」ではない。生特徴量を一次、10要素を二次の派生特徴として使う。

| 分類 | 特徴量 |
|------|--------|
| 市場系 | 人気順位（レース内正規化）、人気の有無、控除率補正済み暗黙勝率、log(単勝オッズ)、レース内オッズ順位、オッズの有無 |
| 馬体・斤量 | 馬体重のレース内z-score、馬体重増減、斤量（基準差・z-score）、馬体重の有無 |
| 通算成績 | log1p(通算出走数)、通算勝率、通算複勝率（`race_entries.career_*`） |
| 前走系（as-of） | 前走の有無、1/前走着順、前走着順の頭数正規化、前走上がり3F、前走着差、log1p(前走間隔) |
| レース内相対化 | log(出走頭数)、ルール総合スコアの z-score と順位 |
| ルールベース派生 | 10要素それぞれ（`ruleScores`） |

特徴量名とベクトル化は `FEATURE_SPECS` 1箇所から導出しているため、
名前と値の順序がズレることは構造上起きない。

> **確定オッズ（`final_win_odds`）は特徴量に入れていない。**
> レース後にしか分からない値なので、回収率の払戻計算にのみ使う。

#### 市場系特徴量は人気順位が主軸

JRA公式の**過去レース結果ページには全馬の事前単勝オッズが載っていない**。
払戻金から復元できるのは1着馬の確定単勝オッズだけである。
これを `race_entries.win_odds` に書いてしまうと
「`win_odds` が非null ⇔ そのレースの勝ち馬」という致命的な look-ahead リークになる。

そのため:

| 列 | 位置づけ |
|----|---------|
| `race_entries.win_odds` | **出走前の表示オッズ** を入れる列。現状は出馬表収集が未実装のため大半が NULL |
| `race_results.final_win_odds` | 払戻金から復元した確定オッズ（1着馬のみ）。回収率の払戻計算にのみ使う |
| `race_entries.popularity` | 全馬ぶん取得できる。**市場系特徴量の主軸** |

`FeatureBuilder` は単勝オッズを
**同一レースの全出走馬に値が揃っている場合のみ** 特徴量に使う
（`hasCompleteOdds`）。1頭でも欠けていれば、そのレースはオッズ由来の特徴量
（`log単勝オッズ` / `オッズ順位` / `オッズ有無`）を **全馬まとめて定数** にする。
部分的な存在自体が「勝ち馬かどうか」の情報になるのを防ぐためである。

市場暗黙勝率（`marketImpliedProb`）は次の優先順位で算出する（`src/features/MarketProbability.ts`）。

1. 全馬にオッズあり → `1/オッズ` をレース内で合計1に正規化（控除率が除去される）
2. それ以外 → 人気順位を人気別勝率テーブル（`POPULARITY_WIN_RATES`）で確率に変換し、レース内で合計1に正規化
3. どちらも無い → 一様分布

この固定テストは
`src/features/__test__/FeatureBuilder.test.ts` の
「市場オッズの部分欠損（勝ち馬のみオッズあり）」と
`src/features/__test__/MarketProbability.test.ts` にある。

##### 既存DBに混入したオッズのクリア

確定オッズ（払戻金由来）が `race_entries.win_odds` に混入したDBに備えて、
`bun start rebuild-stats` が
次の両方を満たす行だけを「結果由来」と判定してクリアする。

1. 同一レースで `win_odds` が入っている馬がその1頭だけ（他馬は全て NULL）
2. その値が同じ出走行の `race_results.final_win_odds` と一致する

出馬表から取り込んだレースは全馬に `win_odds` が入るため、条件1で除外される。

### モデル評価（walk-forward）

k-fold ではなく **walk-forward**（時系列ブロック）で評価する。
レースを日付昇順に並べ、ブロック b の検証には「ブロック b より前のレースだけ」で
学習したモデルを使う。シャッフルはせず、同一レースの馬が学習と検証に跨がることもない。

ブロックの切れ目は **開催日単位** にしている（`splitRacesIntoDateBlocks`）。
JRA の実データは1日24〜36レース（3場×12R）あるため、
分割点をレース索引で決めると境界がほぼ必ず開催日の途中に落ち、
「検証レースと同一開催日の別レース」が学習窓に入ってモデル係数が
同日の結果で学習されてしまう。同一開催日のレースは必ず同じブロックに入れることで、
学習窓には検証ブロック初日より前のレースしか入らない。
（全レースが同一開催日の場合は分割できないので、理由つきで検証をスキップする）

```bash
bun start ml --validate                # 5ブロック / 最小学習150レース
bun start ml --validate --blocks 8
bun start ml --validate --min-train 0  # 学習が少ないブロックも評価に含める
bun start backtest --ml                # バックテストと同時に実行
```

#### 少データ向けの3つの調整

227レース規模では、ブロック1つあたりの学習データが数十レースしかない。
そのまま全ブロックを平均すると「学習データ不足の症状」が総合指標に混ざるため、
次の3点を入れている。

##### 1. λ（L2強度）を学習窓の内側分割で選ぶ（nested / rolling 選択）

各検証ブロックについて、**その学習窓をさらに内側で時系列3分割** し、
rolling（expanding window）の内側検証だけで λ を選ぶ
（`src/models/HyperparameterSelection.ts`）。候補は `[0.01, 0.1, 1, 10, 100]`。

**検証ブロックのレースは λ 選択へ一切渡らない。**
`WalkForwardValidation` が `races.slice(0, testStart)` だけを
`tuneOnTrainWindow()` に渡す構造になっており、
「検証ブロックのラベルを壊しても選ばれる λ が1つも変わらない」ことを
`src/models/__test__/SmallDataTuning.test.ts` で固定している。

選ばれた λ と内側 fold 数はブロック別の表に出る。
内側分割が作れないほど学習窓が短い場合は候補の中央値へフォールバックし、
`内側fold = 0` として明示する。

市場のみモデル・小モデルも **同じ手続きで独立に λ を選ぶ**ので、
比較表の各列は「同じ条件で最善を尽くしたモデル同士」の比較になる。

##### 2. 最小学習レース数（`--min-train`、既定150）

最初の検証ブロックを開始する前に最低150レースの学習データを要求する。
満たないブロックはスキップし、**総合指標にも較正テーブルにも含めない**。
スキップしたブロックは理由つきで一覧表示する。

実データ（227レース）では学習72レース・144レースのブロックがスキップされ、
学習204レース / 検証49レースの1ブロックだけが残る。
評価レース数が減るのはトレードオフだが、
「モデルの汎化性能」と「学習データ不足の症状」を混ぜないほうが読み手に正直である。

##### 3. 小モデルの並走

市場系6本に、市場と独立な情報を持つ4本を足した **10次元の小モデル** を
同じ walk-forward・同じ λ 選択手続きで並走させ、比較表に列として出す
（`SMALL_MODEL_FEATURE_NAMES`）。

| 追加特徴量 | 選んだ理由 |
|-----------|-----------|
| `前走有無` | 前走系の欠損フラグ。無いと「前走なし＝0」が数値として効いてしまう |
| `前走着順相対` | 直前の実力の最も素直な要約。頭数で正規化してありレース間で比較できる |
| `前走上がり3F` | 着順に出ない末脚を拾う唯一の生特徴（基準36秒との差） |
| `斤量相対` | ハンデ＝主催者による能力評価。市場とは独立に付けられた外部情報 |

外したもの: 通算成績3本（出馬表インポート経由でしか入らず実データでは欠損が多い）、
馬体重系（当日情報で分散が大きい）、ルールベース派生14本（市場系と強く相関し、
少データでは係数が不安定になる）。

「次元を削れば少データでも市場に追いつけるのか」を同じ表で読むための列であって、
これ自体を採用候補にしているわけではない。

実データでは小モデル（2.2094）は34次元の本体（2.1626）より log loss が悪く、
**次元を削っただけでは市場のみモデルに追いつかなかった**。
一方、最小学習レース数を外して181レースで評価すると小モデル 2.1236 / 本体 2.2194 と逆転する。
学習量が少ないうちは小モデルが有利、増えると34次元が追い抜く、という読み方になる。

#### 入れなかったもの: 温度スケーリング

λ 選択と同じ内側分割で温度 `T` を当て、`softmax(logit / T)` で確率を平坦化する
較正手法を実装して測定したが、**改善しなかったので削除した**。

| 設定 | ML log loss |
|------|-------------|
| λ内側選択のみ（最小学習150 / 49レース） | **2.1626** |
| λ内側選択 + 温度スケーリング | 2.1767 |
| λ内側選択のみ（最小学習0 / 181レース） | **2.2194** |
| λ内側選択 + 温度スケーリング | 2.2278 |

較正テーブルも改善しなかった（予測0.5〜0.6帯は温度なし n=2 に対し温度あり n=7 で実績28.6%）。
原因は、内側検証が選ぶ `T` が 0.8〜0.9（= さらに尖らせる方向）だったこと。
λ=100 の強い正則化ですでに確率が十分平坦になっているため、
内側検証では「もっと尖らせたほうが当たる」と判断され、それが検証ブロックへ転移しなかった。
少データでは較正パラメータ1個を別途推定するより、λ を強くして
モデルそのものを縮めるほうが効いている。

| 指標 | 説明 |
|------|------|
| **log loss（主指標）** | レース単位の勝ち馬 log loss（-mean log p(実際の勝ち馬)） |
| Brier | 単勝確率の二乗誤差 |
| 複勝 log loss | 3着以内の二値 log loss |
| top-1 的中率 | 予測1位が実際に1着だった割合 |
| top-3 再現率 | 予測上位3頭のうち実際に3着以内だった割合 |
| Spearman | 予測順位と実着順の順位相関 |
| 単勝回収率 | **実オッズ**での回収率。対象は「全出走馬にオッズが揃うレース」だけ（下記） |

#### 回収率の対象レース（重要）

回収率の集計対象は **全出走馬にオッズが揃っているレース**（`hasCompleteOdds`）に限る。
「賭け対象馬にオッズがあるレース」にしてはならない。

`race_results.final_win_odds` は払戻金から復元するため **1着馬にしか入らない**。
そのため「賭け対象馬にオッズがあるレース」を対象にすると、
**予測1位＝実際の勝ち馬だったレースしか賭け対象にならない**。
回収率は「的中したレースだけを賭けた回収率」＝ 平均単勝配当に化け、
的中率×平均配当の数百％という無意味な数字が出る。

対象レースが0件のときは `roiRaces = 0` で **算出不能** と表示する。
表に出る `0.000` は「回収率0%」ではない。

```
  ※ 回収率は **算出不能**（全馬に事前オッズが揃うレースが0件）。表の回収率0は「0%」ではない
```

事前オッズ（`race_entries.win_odds`）は出馬表インポート経由でしか入らないため、
**オッズの無いレースしか蓄積していないデータでは回収率は常に算出不能になる**。
これは正しい挙動であって、バグではない。

旧実装にあった Accuracy / Precision / Recall / F1 / AUC は廃止した。
理由: ハードラベル（0/1）で計算された「AUC」は実態が balanced accuracy であり、
また確率予測の良し悪しは閾値依存の指標では測れないため。

較正テーブル（予測確率の帯ごとの平均予測と実績勝率）も同時に出力する。

### 採用ゲート

MLを予想の主軸にしてよいかは、以下の2条件を **両方** 満たすかで判定する。
**どちらも基準は「市場特徴量のみで学習した同型モデル」である。**

1. 勝ち馬 log loss が市場のみモデルを **下回る**（確率としての良さ）
2. top-1 的中率が市場のみモデル **以上**、または Brier が市場のみモデル **以下**
   （順位づけ・二乗誤差のどちらかで負けていない）

#### ゲート②を「top-1 > ルールベース」から市場基準へ変えた理由

旧ゲート②は「top-1 的中率がルールベース（10要素）を上回る」だった。
これは **現データでは検定として機能していない**。

実データ227レースでのルールベースの top-1 は **9.9%** で、
1レース平均16頭立てのランダム選択（約6%）とほとんど変わらない。
一方 ML は人気順位を特徴量に持つので top-1 は33〜37%出る。
つまりゲート②は「人気順を見ているモデルなら無条件で通る」状態であり、
ゲート全体の判定は実質ゲート①だけで決まっていた。

そこで基準を市場側へ移した。ゲート①（log loss）は確率の良さ、
ゲート②（top-1 / Brier）は順位づけと二乗誤差を見るので、
「log loss は僅差で負けたが順位づけは市場より良い」といった状態を
表に出したうえで、採用判定は①が必須という形を保てる。

`または` にしてあるのは、この2指標が少データでは別々に振れるためである
（実データでは top-1 は ML 36.7% > 市場 34.7% で勝ち、Brier は 0.0536 > 0.0524 で負けた）。
両方を要求すると、評価49レースの揺らぎでゲートが開閉してしまう。

ルールベースの top-1 は **参考表示** として出力に残す（判定には使わない）。

#### ベースラインは4種類ある（何と比べているかに注意）

| ベースライン | 中身 | 用途 |
|-------------|------|------|
| **市場特徴量のみモデル** | 本体と同じ walk-forward・同じ λ 選択手続きで、市場系特徴量（人気・市場暗黙勝率・オッズ）**以外をゼロ埋め**して学習した同型モデル（`maskToMarketFeatures`） | **採用ゲート①②の判定基準** |
| 小モデル | 市場系6本 + 前走有無・前走着順相対・前走上がり3F・斤量相対 の10次元（`maskToSmallModelFeatures`） | 参考表示。次元数の効き方を見る |
| 人気別勝率テーブル | `POPULARITY_WIN_RATES`（人気順位→勝率の固定表）をレース内正規化したもの。全馬にオッズが揃うレースではオッズから算出する | 参考表示のみ。判定には使わない |
| ルールベース10要素 | スコアリングモデルの合計点 | 参考表示のみ（現データではほぼランダム） |

**「人気別勝率テーブル」を採用ゲートの基準にしてはならない。**
実データでは `hasCompleteOdds` がほぼ常に false なので、このベースラインは
「人気順位 → 固定勝率表 → レース内正規化」に過ぎない。一方 ML は
同じ `popularity` と、そこから作った `marketImpliedProb` を特徴量として持っている。
つまり ML は「同じ情報から、データに合わせて表を学習し直したモデル」であり、
log loss で固定表を下回るのは **ほぼ自明**。これを基準にすると
ゲート①は実質無条件で通ってしまう。

また、この表は市場そのものではないので、これを下回っても
「市場を上回った」とは言えない。上回ったのは人気別勝率の教科書値である。

そこで、ゲート①の基準は **同じ市場情報だけを与えて同じ手続きで学習した同型モデル**
にしてある。これを下回って初めて「市場情報以外の特徴量が寄与している」と言える。

市場暗黙確率の算出元（オッズか人気順位か）は `ml --validate` / `backtest` の
出力に明示される。

```
  ① log loss < 市場特徴量のみモデル: ❌ (ML 2.1626 vs 市場のみモデル 2.1390)
     ※ 参考: 人気別勝率テーブル 2.1354（固定表なので判定には使わない）
  ② top-1 ≧ 市場のみモデル または Brier ≦ 市場のみモデル: ✅
     top-1  ML 36.7% vs 市場のみモデル 34.7% / Brier  ML 0.0536 vs 市場のみモデル 0.0524
     ※ 参考: ルールベース top-1 10.2%（現データではほぼランダムなので判定には使わない）
```

#### 実データでの現状（2026-09 時点 / 227レース・3,293出走行）

少データ調整を入れた前後の総合指標。

| 指標 | 調整前（λ=1固定・全ブロック） | 調整後（λ内側選択・最小学習150） |
|------|---------------------------|------------------------------|
| 評価レース数 | 181 | 49 |
| ML 勝ち馬 log loss | 2.3621 | **2.1626** |
| 市場のみモデル log loss | 2.0502 | 2.1390 |
| ML top-1 | 0.337 | 0.367 |
| ML Brier | 0.0585 | 0.0536 |
| 較正（予測0.5〜0.6帯） | 平均予測54.4% / 実績18.5% | 平均予測53.9% / 実績0.0%（n=2） |

評価レース数が変わるので前後の log loss を直接は比べられない。
**同じ181レースで λ 選択だけを入れた場合** は 2.3621 → 2.2194 で、
λ の内側選択それ自体に約 0.14 の改善がある。

ゲート①は依然として未通過だが、差は 0.312 → 0.024 まで縮んだ。
自信過剰（予測50%超の帯で実績が大幅に下回る）も、
予測0.5超に入る行が27件から4件へ減ったことでほぼ解消している。

> **限界**: 「市場特徴量のみモデル」も、実データでは結局 `popularity` しか
> 実質的な情報を持たない（事前オッズが無いため）。
> 事前オッズを収集できるようになるまでは、このゲートは
> 「人気順位以外の特徴量が寄与しているか」の検定であって、
> 「実際の馬券市場に勝てるか」の検定ではない。

ゲートが ❌ の間は、`race-list` などの表示では **ルールベース10要素を主** とし、
ML確率は参考値として併記する（`.claude/skills/race-list/SKILL.md` に記載）。

### ルールベース10要素の位置づけ

廃止しない。以下の3役で使い続ける。

1. **特徴量**: `ruleScores` として ML に入力する
2. **説明**: なぜその馬が高い／低いかを人間に説明する内訳
3. **ベースライン**: 採用ゲートの比較対象

## 重み最適化（非推奨・説明用射影）

> **`optimize-weights` は予測器としては廃止した。**
> 現在は「ルールベース10要素のうち、どれが着順と線形に結びついているか」を
> 人間が読むための **in-sample な射影** として残しているだけである。
> 予測の良し悪しは `ml --validate`（walk-forward）で判断すること。

### なぜ予測器として使えないか

1. **in-sample 比較**: 学習に使ったデータでそのまま誤差を比較しているため、
   「改善率」はホールドアウトでの改善を意味しない。
2. **切片なし・負値クリップ**: 負の重みを0にクリップして合計1に正規化するため、
   得られる係数は最小二乗解でも確率モデルの係数でもない。
3. **目的変数が着順の線形変換**: `1 - (着順-1)/17` は出走頭数に依存し、
   レース内の相対評価にもなっていない。

出力された数値をそのまま `SCORE_WEIGHTS` に反映してはいけない。

### 実装ファイル

```
src/models/MachineLearningModel.ts (optimizeWeights / runQuickOptimization メソッド)
```

### 実行方法

```bash
bun start optimize-weights
bun start optimize-weights --lambda 0.05
bun start optimize-weights --output   # 参考値としてコード形式で出力
```

## 最終予想の生成

**ML確率を主、ルールベース10要素を理由の内訳** として最終予想を生成します
（`.claude/skills/race-list/SKILL.md`）。

ただし `ml --validate` の採用ゲートが未通過、またはデータ不足で検証できない場合は
**ルールベースを主に切り替える**。この主従関係は必ず予想の冒頭に明記すること。

### 予想出力形式

```
最終予想（スコアリング × ML総合判断）

◎ 本命: 12番 クリオロゴールド
○ 対抗: 11番 ツルノマイハシ
▲ 単穴: 13番 シャインフォーミー

スコア×ML比較表
予想理由（両モデルの観点から）
穴馬候補
懸念点
買い目提案
```

### 本命・対抗・単穴の選定基準

| 印 | 選定基準（採用ゲート通過時） |
|----|---------|
| ◎ 本命 | ML単勝確率1位 |
| ○ 対抗 | ML単勝確率2位、またはルールベース1位でML上位 |
| ▲ 単穴 | ML確率が市場を大きく上回る（妙味が大きい）馬 |

### 穴馬候補の選定

- ML単勝確率が市場暗黙確率を明確に上回る馬（妙味 = 単勝 − 市場 が大きい）
- 10要素の内訳で、特定要素が突出している馬

### 買い目提案

| 馬券種 | 提案基準 |
|--------|---------|
| 単勝 | 本命馬 |
| 馬連 | 本命×対抗 |
| 3連複 | 本命×対抗×単穴 |
| ワイド | 本命-対抗、本命-単穴、対抗-単穴 |
